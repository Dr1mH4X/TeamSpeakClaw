# Agent Note: 短反馈音频走预生成 PCM 缓存与播报回合

Status: implemented

## Problem

语音路径缺两类即时反馈：模型开始调工具后用户听不到任何动静（工具耗时从几百毫秒到数十秒），只喊唤醒词时也要等 STT + LLM + TTS 才有回应（数秒），用户无从判断是否已被唤醒。

## Decision

- 短语按触发点分成常量池（`FeedbackGroup`）：`web_search` 取「我来看看」/「我来搜索下」，其余工具取「我来研究下」，唤醒确认取「嗯哼」/「在呢」。不做配置：命中率取决于模型对工具名的选择，配置项只增加维护面。
- 每个池有自己的轮换游标（`FeedbackPlayer::cursors`）：同一触发点连续触发时轮换取一条，不会反复同一句；游标归播放器而非回合，所以跨轮次也继续轮换。
- 短语在启动期由本轮 TTS 的同一个 provider 合成一次（`feedback_phrases()` 是各池的并集，池之间不重复），解码成 48k 立体声 PCM 缓存（`decode_to_pcm_48k_stereo`，ffmpeg 只在预热时各跑一次）；触发时取该池轮换到的那条，以 `AudioOutput::enqueue_pcm_clip_with_cancel` 入队 PCM 片段，首帧只剩进程内 opus 编码。预热失败只记日志，首次触发按需重试。
- 工具提示音在本轮第一次工具调用开始执行时立即入队（`ToolFeedback` 的 `announced` 置位后静默），与工具耗时无关；片段与本轮各条 TTS 流共用回合播放取消位，插话时一起停声。
- 提示音的取消位就是回合持有的播放取消位（`ActiveTurn::playback_cancel`），与本回合各条 TTS 流共用（[TTS 会话按 LLM 流创建，工具轮与最终回复各占一条](../../implemented/bug-fix/2026-10-03-tts-session-per-llm-stream.md)）：插话取消回合时提示音与回复一起停。这类片段不登记进 `stop_clips` 的取消集合——那批取消位属于工具片段，登记进去会让「停止播放」连带取消本回合的 TTS 播放。
- 唤醒确认音挂在唤醒门的命中判定上：命中点之后 VAD 活跃语音不足 `WAKE_ONLY_TAIL_MS`（200ms）即判「这条 utterance 只有唤醒词」，播确认音并丢弃该 chunk，不再进 STT/LLM；判据是流式累计的活跃毫秒数，不是音频长度（[唤醒门逐帧喂入，命中即插话](../../implemented/feature/2026-10-03-wakeword-per-frame-gate.md)）。确认音同时 `WakeGate::refresh_window`，把开门窗口从确认时刻重算。
- 确认音没有真实回合，就地登记一个「播报回合」并 `mark_producing`：`TurnRegistry::producing_turn()` 因此能看到它，后续唤醒词可插话取消，「嗯哼」的回声也按既有「忙」语义丢弃。播完（或被取消）后由等待任务放出句柄，等待有 10s 上限——消费者停摆时不能留一条「永远产出」的条目把后续语音全判成忙。
- 工具提示音挂在两条语音回路上：STT（`handle_user_input` 的 `tool_feedback`）与 omni（`handle_omni_audio_chunk`）都置真，两块共用同一 `ToolFeedback`、`FeedbackPlayer` 与句段缓存；桥接文本不挂，文本回复本身即反馈。

## Alternatives considered

- **触发时实时合成**：TTS 首包冷启动几百毫秒起，再排队进输出通道，反馈就失去意义；预热把这段挪到启动期。
- **每个触发点只留一条短语**：听起来固定、像卡带，尤其唤醒确认会一天响很多次；池内轮换没有额外成本，预热时多合成一条而已。
- **每池随机取一条**：要引入随机数依赖或自造随机源，而且会出现连续两次抽到同一句的观感；轮换是可预期的均匀分布，也便于单测。
- **提示音延迟一段时长才播（工具秒回时不播）**：能避免短工具下提示音与回复紧挨着，但用户喊完工具名到听见动静之间是沉默，机器人与「没听见」无从区分；提示音只是排队播放的几百毫秒片段，最坏情况是把回复推后一个片段时长。
- **每个工具调用各播一次**：模型常在一轮里连续调多个工具（并行调用与工具循环的多轮），几百毫秒的片段首尾相接会把正式回复越推越后，而用户只需要知道「它在干活」。
- **缓存编码音频、复用 EncodedStream 段通道**：省掉 PCM 转换，但播放热路径要再起 ffmpeg 解码进程，而且当前流的 TTS 会话在工具调用前就已随 `finish_reason` 关掉（会话生命周期 = 单次 LLM 流），工具时刻往里推段会落到已收尾的会话上。
- **提示音作为独立 FIFO 作业排在当前回合之后**：FIFO 里它排在本轮 TTS 会话作业之后，而该作业在首个句段到达前一直占着通道，提示音会被压到回复之后；PCM 片段与「先关会话再执行工具」的既有顺序相容。
- **提示音自持独立取消位**：插话就只停回复、不停提示音，或在插话路径里按来源分别置位；共用回合取消位让「一次插话停掉本轮全部出声」成为默认语义。
- **唤醒确认音沿用「丢弃触发命中的整条 utterance」**（[命中唤醒词的 utterance 整体下行](../../implemented/feature/2026-10-02-wakeword-utterance-passthrough.md) 的否决项）：同声短指令（「唤醒词 停」）会被误丢。本判据只用于确认音与丢弃唤醒词独占的 chunk，仍承担同一代价：紧跟唤醒词、活跃语音不足 `WAKE_ONLY_TAIL_MS` 的指令会被判成独占而丢掉；要无损时改成只播确认音、chunk 继续下行。
- **工具提示音只在 STT 路径挂（omni 保持静默）**：omni 音频轮与 STT 轮在用户感知上没有区别，都是「说完等结果」，静默只是让 omni 用户多一段无声等待；两条路径共用 `router/turn.rs` 的 `TurnRequest::run` 与 `TtsTurnRuntime`，`build_tts_callbacks` 已在同一处建 `ToolFeedback`，挂上不需要新代码。
- **把播报回合的产出标记延长到 VAD 尾音（`VAD_SILENCE_MS`）之后**：能顺带挡住短反馈的音箱回声，但会连正常短指令一起丢；回声仍按既定的 AEC 方向处理。

## Consequences

- 所得：本轮第一次工具调用时用户即刻听到「我来看看」/「我来搜索下」/「我来研究下」，STT 与 omni 两条语音回路一致，连续的工具轮不会叠播，回复紧随其后；只喊唤醒词得到 600ms 级确认音（「嗯哼」/「在呢」轮换），而不是数秒后的 LLM 回复；两条功能共用一份短语缓存与一条播报路径。
- 代价：TTS 不可用（未配置、provider 失败或未启用）时两类反馈都静默跳过；秒回的工具也会让回复晚一个片段时长开始；一轮里第二个工具起不再有声音提示；短反馈是 UI 层反馈，不进对话历史、不作为 assistant 消息回喂模型；「只喊唤醒词」不再产生 LLM 轮次，`preprocess_stt_text` 的短句放行语义不受影响。
- 验证：`cargo fmt --check`、`cargo clippy --all-targets --locked -- -D warnings`、`cargo test --all-targets --locked`；`voice_feedback` 覆盖短语池与工具分组、池内轮换、预热清单去重、纯唤醒词判据、一轮首次工具调用即刻入队与后续静默、取消后静默，`audio_output` 覆盖 PCM 预热解码与回合片段取消位，`tool_loop` 覆盖工具开始回调在工具执行之前。实机需确认五条短语的首帧与插话取消。
