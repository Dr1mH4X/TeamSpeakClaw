# Agent Note: 发版日志是仓库文件而非生成产物

Status: implemented

## Problem

每个版本的发布说明都要面向使用者说明这一版改了什么、要不要动手，但提交标题只描述改动本身，写不出「config/prompts.toml 不再被读取，请删除该文件」这类判断。一个版本里几十条提交还需要按新增、修复、重构归类，并挑出真正需要使用者动作的部分；这件事依赖对整段历史的通读，不可能从单条提交的主题里机械地推出来。

同时发布说明需要可评审、可回溯：改动合并之前就要能看到这一版将如何对外描述，合并之后又能在仓库里查到某一版究竟承诺了什么。

## Decision

每个版本的 Release 正文是仓库里的一篇文档：`docs/release/<tag>.md`，文件名与 git tag 完全一致。它在发版前与该版改动同一个 PR 提交，由 agent 按 `git log <上一版>..HEAD` 归纳写成，`docs/release/AGENTS.md` 固定其分类顺序、写法与生命周期：分类节只写有内容的，`## 升级注意` 只在有人需要动手时出现，`## 贡献者` 只列人类账号。

`.github/workflows/release.yml` 在 tag 推送后先按 tag 拼出路径，文件缺失就报错终止发布，存在则交给 `softprops/action-gh-release` 作为正文。git-cliff 的配置与 changelog workflow 随之删除。tag 打完后日志冻结，下一版写新文件；只有事实写错才回头修改已发布的日志。

## Alternatives considered

- **继续用 git-cliff 生成**：正文停留在提交标题的粒度，写不出升级动作与影响面；想改一句对外文案就得改提交信息。生成器也让发布说明成为提交历史的副产物，而不是一个可评审的交付物。
- **只在 PR 描述里写、发布时手工粘贴**：发布说明与 tag 失去对应关系，事后无法在仓库里检索某一版的原文；发布者每次都要重新通读整套提交。
- **用 GitHub 自动生成的 release notes**：与 git-cliff 同样只能按标签与提交标题归类，仍然无法表达「谁需要做什么」；仓库里也没有可评审的文稿。
- **把日志留在 CI 里作为 artifact**：正文不在仓库，无法与产生它的改动一起评审，也没有版本化的历史。

## Consequences

发版前必须先提交 `docs/release/<tag>.md`，否则 release job 失败——这是有意为之的硬门禁，缺日志的 tag 不会产生没有正文的 Release。

日志与该版改动同一个 PR 评审，因此评审者能在合并前看到对外表述；写日志的成本落在发起发版的 agent 身上，而不是落在提交标题的措辞上。

格式没有自动校验：仓库没有 TypeScript 工具链，也没有为日志加脚本。格式与分类顺序靠 `docs/release/AGENTS.md` 与 `tsc-release-log` 技能约束，实际门禁是 CI 对文件存在性的检查。

日志冻结在 tag 之后，因此「某一版说了什么」不会随后续改动漂移；需要更正事实时改已发布的日志，并在提交信息里说明改的是哪一处。
