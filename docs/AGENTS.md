# AGENTS.md — 文档标准

本文定义 docs/ 文档体系的分层归属、写作规则与字数预算。写或改 docs/ 下任何文档前先读本文件；超限事实按「字数预算」的两步流程处理。

## 分层归属：一事实一归属

每类事实只有一个归属地，其余地方只放链接，禁止重复。归属判断先问一句：这条事实是给谁看的、属于哪个层次。

| 层级 | 职责 | 不该放这里 |
|---|---|---|
| 根 `AGENTS.md` | 全局 standing orders：每个 session 都必须知道的规则与拓扑，每条一两行并链向归属地 | 展开细节、步骤式流程、任何从归属地重复的内容 |
| `docs/architecture.md` | 有序拓扑：布局含义、入口流、关键代码路径、路由/适配器组成、LLM 引擎 | 逐模块明细（→ 源码）、开发流程、决策理由 |
| `docs/development.md` | 开发流程与环境：构建依赖、日常操作、git 约定、子代理与输出规范 | 架构图、测试约定、决策理由 |
| `docs/testing.md` | 测试约定：单测摆放、`#[test]`/`#[tokio::test]` 标注、命名与断言、CI 测试门 | 测试用例誊写 |
| `docs/defensive-patterns.md` | 编码反面与替代：FAILFAST、YAGNI、警告压制处置、类型安全优先 | 常规开发流程 |
| `docs/ci-cd.md` | 各 GitHub Actions workflow 的触发条件与职责 | 架构决策 |
| `docs/agent-notes.md` | 决策记录：为什么这么做、放弃了什么、如何验证；已落地条目用现在时描述现状 | 迁移计划、验收清单、spec 语气 |
| 源码内 `.instructions.md` | 模块级规则，如 `src/config/.instructions.md` | 仓库级规则（→ 根 AGENTS.md） |
| `website/` | 面向最终用户的文档 | 内部实现、引用目录、决策历史 |

放置速查：standing orders → 根 `AGENTS.md`；拓扑/关键路径 → `architecture.md`；开发流程 → `development.md`；测试 → `testing.md`；编码反面 → `defensive-patterns.md`；workflow → `ci-cd.md`；决策理由 → `agent-notes.md`；模块规则 → 源码内 `.instructions.md`；用户文档 → `website/`。

## 写作规则

- **只写当前状态，不写变更史。** 不用「之前/现在/不再/曾改名/已迁移」等说法，不写 PR 或 commit 编号，只写当前机制本身；变更故事归 commit、PR 与 agent-notes。

- **一段一物理行。** Markdown 每段只占一行，用编辑器软换行；代码块、表格、列表结构保持原格式。

- **相对 Markdown 链接。** 引用其他文档用仓库内相对路径，禁用绝对路径与纯文件名参引。

- **禁 emoji**，禁叙述历史与变更叙事（不写「我们后来发现…」这类过程性文字）。

- **用语审核。** 避免 contract、boundary、shape 这类模糊隐喻词，必须使用时先给出准确定义；例如用「响应字段」「JSON 校验」「模块导出」替代「响应形状」「校验边界」。

## 字数预算（中文词数估量）

| 文档 | 预算 |
|---|---|
| 根 `AGENTS.md` | ≤1600 |
| `docs/architecture.md` | ≤1800 |
| `docs/` 其余文档（development / testing / defensive-patterns / ci-cd / agent-notes） | ≤1200 |
| 本文件 `docs/AGENTS.md` | ≤800 |

预算只列 docs/ 将落地的文档；超出时按下述两步处理，不能直接删掉有价值内容：

1. **relocate**：把属于其他层级的事实移过去，原处留一行链接。
2. **condense**：仍超限的压缩措辞。

预算是可突破的护栏而非减负目标；预算本身过低也是预算的缺陷。

## 精简版 slop checklist

写完逐条自查：

- **重复已有规则**：同一规则在多个文档出现。搜一个特征短语定位，只留一个归属地，其余放链接。

- **叙述历史**：出现「之前/现在/不再/重命名/迁移」，或时间线式编排。改为陈述当前事实。

- **手抄目录树**：源码或生成器已是事实来源时，不手工誊写目录、清单或清单式状态。

- **段落墙**：一个长段落塞进多条规则与括号补充。拆段，或把细节降级到它的归属地。

- **强调通胀**：到处加粗、大写、「务必/关键」等于没有强调。只保留会改变行为的那处强调。

- **spec 语气**：用「应当/需要实现」规划未来，而不是「是/采用」描述现状。

- **CoT 泄漏**：残留设计讨论、推测性规划、评审表演。只留结论与必要的归属链接。
