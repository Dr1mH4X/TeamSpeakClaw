# AGENTS.md — 发版日志

本目录存放每个版本的 Release 正文，一篇一版：`<tag>.md`，文件名与 git tag 完全一致。`.github/workflows/release.yml` 在打 tag 时以 `docs/release/<tag>.md` 作为 GitHub Release 正文、以 `Release v<版本>` 作为 Release 标题，文件缺失或日志首行不合格式就直接失败——所以这一版要发布，先把文件写好。本目录在本仓库第一次发版前是空的。

写一篇日志用 [.agents/skills/tsc-release-log/SKILL.md](../../.agents/skills/tsc-release-log/SKILL.md)。发布流程与 workflow 职责见 [../ci-cd.md](../ci-cd.md)。

## 生命周期

日志在发版前写下，与该版的改动一起提交；tag 打完之后冻结，下一版的改动进下一篇。只有事实写错时才回头修改已发布的日志，并在提交信息里说明改的是哪一处事实。

## 文件格式

第一行是 `# <版本> (<发布日期>): <主要更新简述>`：版本是 tag 去掉前缀 `v`，日期取发版当天（回填旧版本时取该 tag 的日期），简述概括这一版的主线，例如 `# 0.6.2 (2026-10-03): 唤醒词与语音反馈`；GitHub Release 的标题是 `Release v<版本>`，与 tag 同名，与这一行无关。随后一段总述（一到三句，说明这一版的主线与影响面），然后是分类条目、可选的「升级注意」与「贡献者」。

分类小节只用这四个名称，按此顺序出现，且只写本版实际有内容的分类：

```
## 新增
## 修复
## 优化
## 其他
```

归类的判据是读者视角：`新增` 收新能力与新的对外行为，`修复` 收缺陷修复（含安全修复），`优化` 收体验、性能与重构，`其他` 收文档、测试、CI、依赖与维护。

之后可以出现：

```
## 升级注意
## 贡献者
```

写法规则：

- 每条一句话，写**行为或归属上的变化**，不抄提交主题原文，不写函数名清单；配置键、CLI 参数、环境变量要写出确切名字。
- 首行的简述是这一版主线的几个字概括，语气与总述第一句一致，不重复总述第一句；没有单一主线时取最贴近的一条（如「多项修复与维护」）。
- 首行的版本必须等于 tag 去掉前缀 `v`，日期写成 `YYYY-MM-DD`；`release.yml` 按这三段校验首行，不合格式即终止发布。
- 能确定来源时在句末附 `（#<PR 号>）`，便于溯源。
- `## 升级注意` 只在有人需要动手时出现：谁受影响、要做什么。整节没有内容就删掉整节，不写「无」。
- `## 贡献者` 列出本版的人类贡献者 `@handle`，机器人账号不计。
- 禁 emoji；一段一物理行；不写内部行号与 `file:line` 引用；不写这一版之外的计划或承诺。

模板：

```markdown
# <版本> (<发布日期>): <主要更新简述>

<一到三句总述：这一版的主线与影响面，以及是否需要使用者动手。>

## 修复

- <行为层面的修复>（#<PR 号>）

## 优化

- <体验、性能或归属上的变化>（#<PR 号>）

## 贡献者

- @<handle>
```
